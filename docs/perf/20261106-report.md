# Performance report, 2026-11-06

What a person feels in Studio, measured from start to first paint through merge: where the
cost comes from, what changed, and the instruments left behind so the next person can measure
the same way.

## Machine and data

- Linux 4.19 under gVisor, 2 cores, 64 GB, no GPU and no perf events. GPUI drew offscreen
  through lavapipe (`mesa-vulkan-drivers`).
- Studio at `6f1b9ad` (main) plus the pull requests below, `release-fast` profile.
- Omnigraph `v0.14.0` release binaries (`omnigraph`, `omnigraph-server`).
- The development graph (`script/dev-server`): 200 people, 25 companies, 40 projects, about
  970 edges.
- A large graph (`script/dev-big-server`, new): `Account` has 95 columns (every scalar kind) and
  100,000 rows. It also has 1,000 tags, 50 regions, 500,000 `Follows` edges and 300,000 others,
  about 340 commits (each load chunk is one, plus 200 edits) and 40 branches with a commit each.
- A slow network: `script/latency-proxy.py --rtt 100` (new) in front of each server.

Wall-clock time on this box is noisy. In addition, gVisor's thread clock ticks in 10 ms, so a
single frame's CPU time reads as 0 or 10 ms. So the scores are counts, which are exact on any
machine:

- requests by route,
- Studio's queries by name,
- the main thread's allocations per frame,
- views drawn per frame,
- the heap.

Time is reported as the main thread's CPU **mean** over all frames, plus wall p95, and is
indicative only. Before and after are compared only within one session. Valgrind (callgrind)
does not start under gVisor (SIGSEGV in `rtld`), so per-function attribution was done by A/B on
allocation counts and by `gdb` stack sampling.

## Instruments (PR #90)

- `studio_perf`, a layer-0 crate with no dependencies. It keeps tallies that are always on:
  requests by method and route template, each `/query` by the name Studio gave the query it
  built, and draws of 24 costly views. With `OMNIGRAPH_STUDIO_TRACE` set it also records Chrome
  trace spans: each request and each answer's decode. It records no token, query text or row
  data.
- The snapshot tool now prints a line per step: time until the step's last request ended,
  requests and bytes, queries, allocations, views drawn, the frame drawn after it, and the heap.
  `measure` adds allocations and views drawn per frame and the mean CPU.
- `script/measure-frames` gained modes:
  - frames (as before, plus canvas pan and zoom and a sidebar resize),
  - `--scenarios` (whole interactions),
  - `--memory` (open and close tabs repeatedly),
  - `--all`.
  It adds the large graph's cases when that server is running.
- `script/dev-big-server`, `script/dev-seed-big.py` and `script/latency-proxy.py`.
- A guard test, `type_table` `opening_a_table_reads_each_relationship_once`.

Building them found a bug in the old instrument. `measure:<n>,type` timed a draw made before
the key's notifications were applied, and GPUI's test mode then drew the real frame after the
timing ended. Every key frame was therefore drawn twice, and the timed draw was the wrong one.
A frame is now one update, timed from outside, and GPUI draws it once as the update ends.

## Where the cost comes from

### Frames

Every frame redraws the root `Workspace`, and on a table the `TypeTable`, because GPUI marks
every view around a notified one for drawing (`Window::mark_view_dirty`). A frame that only
notifies the root costs 0.5 ms and 2,520 allocations on an empty window, and 1.5 ms and 3,475
allocations with the Person table open. A table scroll adds the grid: about 4 ms and 18,500
allocations.

The grid's per-frame work, found by taking one part of a cell out at a time behind an
environment variable and comparing allocations per scroll frame (Person, 22,076 to start):

| taken out | allocs/frame | share |
|---|---|---|
| hidden ⤢ buttons in every writable text cell | 19,776 | 10% |
| hidden Peek buttons in every row | 21,243 | 4% |
| both (kept, PR #92) | 18,768 | 15% |
| relationship cells (counts and tags) | 17,516 | 21% |
| tooltips on relationship and date cells (measured after the hover change: 18,772 to 18,016) | 18,016 | 4% |
| cell click listeners | 21,261 | 4% |
| the row checkbox | 21,731 | 2% |

`gdb` samples of a long scroll put the main thread in GPUI's layout (taffy), prepaint and
paint of many small elements. No single Studio function stood out, so the lever is how many
elements a frame builds.

### Requests

- **Start** sends 8 requests in two waves: health, graphs, access, schema, snapshot and branches
  together, then the head probe (`studio_head`) and a commit page. The snapshot does not name its
  commit, so the probe is needed. At +100 ms per round trip the start takes 378 ms.
- **Opening a table** sends the page, then each relationship column's degrees and neighbours (6
  columns on Person, 12 requests). Eight read slots (`READ_CONCURRENCY`) send them in two waves,
  so the open takes 3 round trips (434 ms at +100 ms), where 2 is the least possible. Re-opening
  the same table sends nothing: the session's memo answers. The new guard test holds this at one
  read per column and kind.
- **A review** reads the merge base, then the changes after it, then a merge dry run, in series
  because each needs the one before (387 ms at +100 ms). A merge is 4 round trips.
- **History** on the large graph reads 21 commit pages and the changes of each commit drawn (27).
  The 21 pages are the branch's page plus the heads of 20 other branches, for tags
  (`OTHER_BRANCHES`). The change reads take about 270 ms each on the server, 4 at a time (the
  long-read slots), so the change counts fill in over 2 to 3 s. Both are bounded by design.

### The server, at scale (E39)

Opening `Account` (95 columns, 100,000 rows) takes 957 ms for one 305 KB request, of which
Studio's decode is 3.5 ms (trace). Asked directly:

| read | time |
|---|---|
| `order { $n.@id } limit 100`, returning `$n` | 0.91 s |
| the same, returning `$n.slug` | 0.08 s |
| `$n`, no order | 0.03 s |
| `$n.@id = $id`, `limit 1` | 0.43 s |
| `$n.@id in $ids` (101 ids) | 0.46 s |

The engine reads every column of every row before it sorts or filters. That is recorded as
**E39** in spec 012 and `docs/deferred-engine-changes.md`. I tried a Studio-side two-step read
(ids first, then the rows by id) and dropped it: the second step costs 0.46 s, because the
filter is the same full read, so the two together save under half and add a round trip.

### Memory

`script/measure-frames --memory`:

- The heap levels off after the first open of the Person table (26.6 MB before #92, 23.3 MB
  with it) and stays there over ten opens and closes. Re-opens send no requests.
- It stays flat across five query tabs opened, run and closed.
- On the large table, scrolling to about 1,100 loaded rows takes the heap from 10 MB to 102 MB.
  Closing the tab leaves 70 MB: the session's read memo, which is capped by bytes
  (`PINNED_READ_BYTES` 64 MB, `SEEDED_READ_BYTES` 16 MB).

No leak was found.

## Hypotheses

| Hypothesis | Change | Result | Kept |
|---|---|---|---|
| Hover-only buttons built hidden in every row cost a scroll frame | Build Peek and ⤢ only in the pointer's row and cell (PR #92) | −15% allocations and about −14% CPU per scroll and resize frame; keys unchanged | yes |
| The pointer's row can be computed from the list's line height | `TypeTable::line_height` | The line height was the list's height (1,002 px for a 29 px row): a bug that also moved a grouped table's lines when a section loaded above the view (PR #91) | fixed |
| Tooltips on relationship and date cells cost a scroll frame | Take them out | −4% allocations; keeping them needs a frame on every cell crossing | no |
| Per-cell click listeners cost a scroll frame | Take them out | −4% allocations, no measurable time | no |
| A large table's first page can be read cheaper from Studio | Ids first, then rows by id | 0.08 s + 0.46 s against 0.91 s, plus a round trip | no: E39 |
| Opening a tab leaks views or subscriptions | Open and close ten times | Heap flat after the first | nothing to fix |
| A review's three round trips can overlap | The dry run beside the change read | It runs only for a review with changes and only feeds the Merge button | no |

## Not verified

- Metal on macOS, real GPU frame times, and a display-linked frame rate: headless draws on every
  change, so a step's views drawn are an upper bound on an app's.
- Precise per-frame CPU: gVisor's thread clock ticks in 10 ms. Means over 200 frames stand in.
- Trackpad momentum scrolling with a resting pointer (PR #92 recomputes the pointer's row each
  frame, so it should follow).
- On this box 7 tests fail on main and on every branch: they run as root under gVisor and check
  symlinks, unwritable folders and `/proc`. These are `agent_panel` confined and skill,
  `studio_settings` release build, `studio_update` install, and `studio_workspace` process stats
  and persistence. CI runs them.
- `cargo deny` fails on main (the `pin-utils` advisory, #89), and so does `structure`
  (`check-design-tokens.py` on `crates/studio/src/organizations.rs:422`).

## What to measure next

- Relationship cells: 21% of a scroll frame. Fewer elements per tag (one box, not a box around
  a text element) and labels kept as `SharedString` would cut it.
- The root `Workspace` redraw (2,520 allocations) that every frame pays: most of it is the
  action listeners registered each frame, as in Zed.
- Opening a table on a slow network: a third round trip because of the 8 read slots; a server
  route that answers counts per relationship group (E16) would remove most of these reads.
