# Performance report, 2026-11-11

The second run of the Studio performance workflow
(`run-wf-autoresearch-modernrelay-omnigraph-studio-perf-20261111T1000Z-825238`). It counts what a
table frame allocates, finds where the count comes from, and cuts it by 11.5% with two changes.
The person sees nothing different; each scroll or redraw of a table does less work.

## Machine and data

- Linux 4.19 under gVisor, 2 cores, 64 GB, no GPU and no perf events. GPUI drew offscreen through
  lavapipe (`mesa-vulkan-drivers`).
- Studio at `348899d` (main, 0.4.3), `release-fast` profile.
- Omnigraph `v0.14.0` release binaries (`omnigraph`, `omnigraph-server`), checksum verified.
- The development graph (`script/dev-server`): Person has 200 rows, 6 relationship columns.
- An empty operator home (`OMNIGRAPH_HOME`) for every run; see "Lessons" below for why.

## What the numbers are

gVisor's thread clock ticks in 10 ms, so a single frame's CPU time reads 0 or 10 ms, and the
median says nothing. The verdict is the count of the main thread's allocations per frame, which is
the same for the same frame on any machine. Repeated runs of one build gave the same count to the
allocation in every case but two, which moved by 7 and 4. Times are the mean CPU time over 200
frames and the median wall time. They are indicative only, and before and after are compared only
inside one session.

## Lessons from the last run (2026-11-06)

What I read: the report (`docs/perf/20261106-report.md`), pull requests #90 to #93 with their
comments, and what landed on main afterwards.

- **#90, the instruments, was closed without merging and without a comment.** It was 2,276 lines
  over 52 files, and it added a crate that every view depended on. None of it is on main: not
  `studio_perf`, the step lines, the request counters, the latency proxy or the large-graph
  server. The workflow now asks for instruments that are small and live in existing layers. So
  this run's instrument is about 100 lines in the snapshot example and `script/measure-frames`,
  with no new crate and no app code. The other parts of #90 are still missing; see "Next".
- **A dropped hypothesis was later taken.** The last run dropped "per-cell click listeners"
  because it saved 4% of allocations and "no measurable time". On 2026-11-10 Ragnor landed that
  same change (`013abb3`), together with boxing a cell's shaped line, and measured it on an M5 Pro
  (4.7 to 4.4 ms). Lesson: on this box, an allocation count that goes down is the evidence. Do not
  drop a change because the 10 ms clock cannot see it.
- **The existing tool is the one that gets extended.** Ragnor added cases to `measure-frames`
  (`eaa01e4`) rather than taking the tool from #90. This run extends `measure-frames` and the
  snapshot tool too.
- **Reviews:** #91, #92 and #93 merged with no review comments. Bugbot did not run on any of them
  (usage limit). Their CI notes recorded `structure` and `deny` failing on main at the time.
- **What wasted time:** the long tool study and a design that reached into 24 views before any
  change used it. This run measured first and added only the counter that the measurements needed.
- **Retried hypothesis, with changed code.** The last run did not keep "tooltips on relationship
  cells", because keeping them "needs a frame on every cell crossing". Since then #92 added the
  pointer's row and cell (`frame_pointer`), and every row crossing already draws the grid. So the
  code that the earlier verdict relied on has changed, and this run measured the hypothesis again
  (H2).
- **New, found this run:** `measure-frames` measured the person's CLI targets too. Studio lists
  them beside the server it is given, and puts a toast in every frame for each target it cannot
  reach. On this box, four unreachable targets added 180 allocations to every frame.
  `measure-frames` now runs each case with an empty operator home (#98).

## Instrument (#98)

- The snapshot tool's global allocator counts each thread's allocations and bytes. `measure:<n>`
  prints the main thread's allocations per frame (median, p95, max) and bytes (median), and the
  mean CPU time beside the median. `script/measure-frames` prints `cpu mean` and `allocs/frame`
  columns.
- It follows Zed's `bench_metrics::CountingAllocator` at the pinned v1.27.0
  (`crates/bench_metrics/src/bench_metrics.rs`, 1017–1190). A reallocation counts as an
  allocation, as dhat and heaptrack count it. The counts are `const` thread-locals with no
  `Drop`, so counting never allocates. That is the same design that divan's `ThreadAllocInfo`
  uses.
- Rejected: depending on `bench_metrics` itself. It brings criterion and perf-event into the
  `studio` crate's dev-dependencies, and with them into every test build. Its count for one thread
  is reachable only through criterion's `Measurement` trait.
- Rejected again: re-landing #90's `studio_perf` crate (see "Lessons").
- To attribute allocations to their sources I used `heaptrack` (apt), which works under gVisor
  (valgrind does not), and folded its stacks with `heaptrack_print -F`. This needs no code in the
  repository.

## Where a table frame's allocations go

From `heaptrack` over one run of 600 table-scroll frames, its start included (10.3 million
allocations), grouped by the nearest function outside the standard library:

| where | share |
|---|---|
| Taffy computing the layout (`compute_flexbox_layout`, block layout, `new_with_children`) | 45% |
| `Interactivity::new` (each `div`) | 8% |
| `Window::on_mouse_event` (listeners: hitboxes, tooltips, hover) | 7% |
| `TextStyle::default` from `Window::text_style` | 6% |
| everything else, under 2% each | 34% |

The `TextStyle` share comes from `CellText`. It asked `Window::text_style()` three times per cell
per frame, and GPUI builds each answer from a fresh default style, whose font features allocate an
`Arc` (H1).

Most of Taffy's share is in the row structure of Zed's `ui::Table` (a row, a pinned section, a
scrolled section and a wrapper for each cell). Studio cannot change that without forking it.
Studio's own box for each cell is a small part of it (H3).

Then, taking one part of the grid out at a time behind an environment variable (a scratch build,
not committed), table scroll from 15,027 allocations:

| taken out | allocs/frame | change |
|---|---|---|
| relationship cells (drawn as "…") | 11,052 | −3,975 (−26%) |
| …only their tooltip and element id | 13,813 | −1,214 |
| …only their tags (a count stands in) | 12,889 | −2,138 |
| the row checkbox in every row | 14,544 | −483 (−3%) |
| Studio's box around a plain text cell | 14,802 | −225 (−1.5%) |

About two relationship columns are drawn (the one in view and one beyond it), about 50 cells. Each
cell cost about 80 allocations a frame.

## Hypotheses

| # | Hypothesis | Change | Table scroll allocs | Window redraw allocs | Gates | Kept |
|---|---|---|---|---|---|---|
| H1 | `CellText` works out its text style three times a frame | Shape the line as it is laid out, and keep it and its height for the prepaint (#99) | 15,589 → 15,027 (−3.6%) | 15,893 → 15,333 | pass | yes |
| H2 | Every relationship cell carries a tooltip, but only the one under the pointer can show it | Build the id and tooltip only in the pointer's cell; a move onto or off one along a row draws the grid once (#100) | 15,589 → 14,359 (−7.9%) | 15,893 → 14,671 | pass | yes |
| H3 | Studio's box around a plain text cell costs a scroll frame | Draw the text without it | −225 (−1.5%) | | not run | no: too small to lose the padding and the column rule |
| H4 | The row checkbox, hidden in every row, costs a scroll frame | (measured only) | −483 (−3%) | | | not done; see "Next" |
| H5 | Relationship tags cost a scroll frame | (measured only) | about −2,100 | | | not done; see "Next" |

Each of H1 and H2 alone is measured against main with the instrument. Key, canvas, tree, page and
history frames keep the same count with each change.

### H2's trade-off

GPUI starts a tooltip on a mouse move that a listener from an earlier frame handles. With H2, the
move that brings the pointer onto a relationship cell makes the grid draw that cell's tooltip.
The tooltip then shows on the next move, as it did before. If the pointer stops on exactly that
first move, the tooltip waits until the pointer moves again, even by a pixel. In the snapshot
tool: after one move, no tooltip; after two, the same tooltip as main, pixel for pixel (media
below). A real pointer that slows down onto a cell sends several moves. How this feels with a real
mouse was not checked here. The rejected alternative was to send a synthetic mouse move after the
frame.

## Not verified

- Metal on macOS, real GPU frame times and a frame rate tied to the display.
- Per-frame CPU time: the thread clock ticks in 10 ms. Means over 200 frames stand in.
- How H2's tooltip feels with a real mouse or trackpad.
- The large graph (95 columns, 100,000 rows): its seed script and server were in #90, which did
  not land, and I did not seed it again this run. H1 and H2 scale with the cells drawn, not the
  rows loaded, and the 95-column type has relationship columns, so the saving should carry.
- Interactions and requests (see "Scenarios"), and memory.
- Five tests fail on this box on every branch: they run as root under gVisor and check symlinks,
  folders that cannot be written and `/proc`. They are `agent_panel` (confined, skill),
  `studio_update` (install) and `studio_workspace` (persistence, process stats). CI runs them.
