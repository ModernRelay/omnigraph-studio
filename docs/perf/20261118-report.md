# Performance report, 2026-11-18

The third run of the Studio performance workflow
(`run-wf-autoresearch-modernrelay-omnigraph-studio-perf-20261118T1000Z-f51b5a`). It takes the next
step the last run named, relationship tags (H5), and finds that a table beside the inspector draws
cells in columns far past its edge (H6). Together they cut a table scroll frame's allocations by
about a quarter and a frame of the dense graph's tables by about a quarter. The person sees nothing
different, pixel for pixel; each table frame does less work.

## Where a table frame's work went

Two findings, both from reading the code the counts pointed at:

1. **A relationship cell is many elements.** `TypeTable::render_relation_cell` drew a row with
   the count, a row that clips the tags, and a box and a text for each tag: five to seven layout
   nodes in every relationship cell of every frame. Switching only that cell to one element
   (H5) took a scroll frame with the relationship columns in view from 14,354 allocations to
   11,146 (#135 at `6f45e97`).
2. **The table draws columns it cannot show.** `TypeTable::drawn_columns` picks the columns from
   the scroll offset and the *window's* width, since it runs before the grid is laid out.
   Beside the sidebar and the inspector the grid is about 840 of the window's 1,440 px, so every
   row also drew several columns past its edge, among them the Person table's relationship
   columns. That is why the plain "table scroll" fell with H5 too.

### H5: what had to be exact

As merged at #135's head, `6f45e97`. GPUI places an element on device pixels in two steps:
it rounds each length written in code to whole device pixels before layout
(`AbsoluteLength::to_taffy`), then rounds each edge after it
(`TaffyLayoutEngine::layout_bounds`). The element does the same: `Lengths::at` rounds its
written lengths for the scale, and `Rect::snapped` rounds each edge. The first version skipped
the first step and was only as high as its parts, so its parts could land half a pixel from
where the boxes were. A headless test that lays out the old boxes and the element side by side
found it in a cell 32 px high whose count line is 19.5 px, and found parts off at 1.25x and
1.75x. The element now fills the cell, in every cell and under the pointer, and centres its
parts from the cell's whole-pixel top, as the boxes were centred. Under the pointer,
`Tags::tip_fn` puts the tooltip on a box that fills the cell, and the element records the row of
its parts as the tooltip's anchor, so the tooltip hangs where it hung under the row of boxes.
(One earlier version wrapped the cell under the pointer in a box as high as the parts instead;
`f3f77de` replaced it.)

### H6: where the rows find their width

As at #136's head, `a470377`. The columns are picked while the view renders, before the grid is
laid out, so the header, the places and the reads pick from the window's width, which bounds the
grid's (`TypeTable::drawn_columns`). The rows are asked for later, and they pick again. The
header's scrolled strip tracks the table's horizontal scroll handle, and the view lays it out
before the rows (`render_header_row`, then Zed's `Table`). GPUI writes a scrolled element's
bounds to the handle it tracks in that element's prepaint (`clamp_scroll_position`,
`gpui/src/elements/div.rs`), so when the list asks for its lines the handle already holds this
frame's width of the strip the rows scroll, with the pinned column left out. The list asks for
lines more than once a frame: to measure an item, in `request_layout` and in `prepaint`, with
the bounds it had before, and then for the lines in view, also in `prepaint`. That last call
sets the columns the rows draw (`TypeTable::rows_drawn`), and it has this frame's width. So the
review's O2 on #136 is settled: the handle holds this frame's width when the rows are picked,
and #136 takes the width from it. It relies on Zed's `Table` laying out its header before its
body, which is not documented; `rows_draw_only_the_columns_in_view` relies on the same order.

`81c3515` took the width from the list's own bounds less the pinned column. That is also this
frame's width, and it gave the same counts, but it read the uniform list handle's inner state
and subtracted the pinned column's width by hand, which a second pinned column or a gutter
would silently make wrong. #136 lists it as rejected.

The header keeps the window-wide pick. Its cells are built while the view renders, before any of
the frame is laid out, so the most it could know is the width of the frame before. Zed's `Table`
needs every row to have the header's columns, so a row keeps every place and draws an empty box
in a column outside its strip. The reads keep the wider pick too, so a column scrolled into view
has its relationships already. When the inspector closes, the grid widens with the window
unchanged, and the rows draw what it uncovers in that same frame:
`rows_draw_the_cells_their_own_view_meets` checks the first frame after the widening (with a
width one frame old it fails, #136 says), and the frame drawn at `a470377` has main's pixels.

## Next

- **Read only what the rows show.** The reads still follow the window-wide pick, so a table
  beside the inspector reads the relationships of columns it does not show. Reading them on
  sight would cut requests but show "…" for a moment when a column scrolls in; it needs the
  read ledger's numbers (`--reads`) and a decision on the trade.
- **The header's wider pick.** The header still lays out the off-screen columns the rows leave
  empty. It is built before the frame is laid out, so it could leave them out only by the width
  of the frame before, and the frame a dock closes would draw empty headers over drawn cells.
  It is one line of a frame's many; leave it unless a measure shows it.
- **The query results have the same cause.** `QueryEditor::result_places` also picks from the
  window's width, and the results sit beside the sidebar too. With six columns it costs nothing;
  a 63-column result would draw cells past the grid's edge in every row, as the table did (not
  measured). Take the rows' width the same way, through one function beside
  `studio_ui::grid_places` that both grids call, so there is one rule for the width of the rows'
  own strip (O3 in the review of #136).
- **Taffy's share in Zed's table rows** (45% of a frame in the last run) is still the largest
  part. Fewer cells drawn shrank it; the structure of each row is unchanged.
