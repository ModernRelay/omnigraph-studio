# Performance report, 2026-11-18

The third run of the Studio performance workflow
(`run-wf-autoresearch-modernrelay-omnigraph-studio-perf-20261118T1000Z-f51b5a`). It takes the next
step the last run named, relationship tags (H5), and finds that a table beside the inspector draws
cells in columns far past its edge (H6). Together they cut a table scroll frame's allocations by
about a quarter and a frame of the dense graph's tables by about a quarter. The person sees nothing
different, pixel for pixel; each table frame does less work.

## Machine and data

- Linux 4.19 under gVisor, 2 cores, no GPU and no perf events. GPUI drew offscreen through
  lavapipe (`mesa-vulkan-drivers`).
- Studio at `55cb7e2` (main), `release-fast` profile. Every build measured came from one
  target directory, and each binary's checksum was printed with its results (see "Lessons").
- Omnigraph `v0.15.0` release binaries (`omnigraph`, `omnigraph-server`), checksum verified.
- The development graph (`script/dev-server`): Person has 200 rows and 3 relationship columns.
  The dense graph (`script/dense-server`): about 17,000 nodes and 119,000 edges; Artifact has
  5,000 rows, Topic 1,500, each with 10 to 14 relationship groups.
- An empty operator home for every run (`script/measure-frames` does this).

## What the numbers are

As in the last run: gVisor's thread clock ticks in 10 ms, so the verdict is the count of the main
thread's allocations a frame, which is the same for the same frame on any machine. Repeated runs
of one build gave the same count in every case. CPU times are means over 200 frames and are only
indicative; before and after are compared inside one session, builds alternating.

## Where a table frame's work went

Two findings, both from reading the code the counts pointed at:

1. **A relationship cell is many elements.** `TypeTable::render_relation_cell` drew a row with
   the count, a row that clips the tags, and a box and a text for each tag: five to seven layout
   nodes in every relationship cell of every frame. Switching only that cell to one element
   (H5) took a scroll frame with the relationship columns in view from 14,354 allocations to
   11,155.
2. **The table draws columns it cannot show.** `TypeTable::drawn_columns` picks the columns from
   the scroll offset and the *window's* width, since it runs before the grid is laid out.
   Beside the sidebar and the inspector the grid is about 840 of the window's 1,440 px, so every
   row also drew several columns past its edge, among them the Person table's relationship
   columns. That is why the plain "table scroll" fell with H5 too.

## Hypotheses

| # | Hypothesis | Change | Table scroll allocs | Relationship scroll allocs | Window redraw allocs | Gates | Kept |
|---|---|---|---|---|---|---|---|
| H5 | A relationship cell's boxes (two rows, and a box and a text a tag) cost a sixth of a scroll frame | One element lays out and paints the tags and the count (#135) | 13,366 → 11,042 (−17.4%) | 14,354 → 11,155 (−22.3%) | 13,688 → 11,362 (−17.0%) | pass | yes |
| H6 | Beside the inspector, rows draw cells in columns past the grid's edge, because the columns are picked from the window's width | Rows pick again from their list's width in the frame; a column outside it is an empty box (#136) | 13,366 → 10,048 (−24.8%) | 14,354 → 13,919 (−3.0%) | 13,688 → 10,533 (−23.0%) | pass | yes |

Each is measured alone against main. Every other case keeps its count (±1) with each change. H6
sends the same reads as main at every step of the `--reads` scenario.

### H5: what had to be exact

GPUI gives an element its bounds already on device pixels. The first version was only as high
as its parts, so the parts were centred from a snapped origin and could land half a pixel from
where the boxes were. A headless test that lays out the old boxes and the element side by side
found it in a cell 32 px high whose count line is 19.5 px. The element now fills the cell and
centres its parts from the cell's whole-pixel top, as the boxes were centred. The cell under the
pointer keeps a wrapper as high as the parts, because GPUI places a tooltip under its element:
with a full-height wrapper the tooltip sat 5 px lower.

### H6: why the header keeps the wider pick

Zed's `Table` needs every row to have the header's columns. The header is built before layout,
when only the window's width is known. GPUI sets a list's bounds before it asks for the rows
(`uniform_list.rs`, `prepaint`), so only the rows can know their real width in the frame. A row
therefore keeps every place and draws an empty box in a column outside its view. The reads keep
the wider pick too, so a column scrolled into view has its relationships already. When the
inspector closes, the grid widens with the window unchanged, and the rows draw what it uncovers
in that same frame (checked by test and by frame).

## Not verified

- Metal on macOS, real GPU frame times and a frame rate tied to the display.
- Frames at 1x scale: the snapshot tool draws at 2x only. H5's rounding follows GPUI's and a unit
  test covers 1x and 2x.
- Requests: H6 keeps the reads on the window-wide pick on purpose, and `--reads` shows the same
  reads at every step. Reading less is in "Next".
- Memory, and the latency of whole interactions: not measured this run.
- Five tests that fail on this box on every branch (root under gVisor), as the last run found.
